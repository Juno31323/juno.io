# 포트폴리오 플랫폼 · 1단계

기존 개인 사이트를 첫 사용자 `/u/juno/`로 가져오고, 다른 회원도 자신의 프로젝트·소개·디자인을 저장하고 게시하는 앱입니다. Astro 7 + Node 서버 + Supabase Auth/Postgres/Storage를 사용합니다. 운영 중인 루트의 GitHub Pages 앱과 분리되어 있으며, 이번에는 로컬 구현·검증과 배포 준비까지 진행합니다.

## 시작하기

저장소 루트에서 Node 24와 실행 중인 Docker Desktop을 사용합니다.

```sh
npm ci
npm run platform:db
npm run platform:migrate
npm run platform:env
npm run platform:dev
```

주소는 `http://127.0.0.1:4400/`입니다. `platform:env`는 로컬 Supabase의 키만 읽어 무시되는 `platform/.env`에 저장합니다. 기존 루트 `.env`와 운영 Supabase를 수정하지 않습니다. 로컬 기본 포트는 API 54321, DB 54322입니다. 같은 포트를 쓰는 다른 프로젝트가 있으면 `platform/supabase/config.toml`을 먼저 변경하세요.

회원가입 후 이름·아이디·소개를 입력하면 빈 테마로 시작합니다. 기존 민준호의 콘텐츠는 신규 계정에 복사되지 않습니다. 처음에는 비공개이며, 프로젝트를 저장한 뒤 대시보드에서 게시합니다. 코드가 비공개이거나 이미지가 없어도 등록할 수 있습니다. 소개·프로젝트·디자인 저장은 초안만 변경하고, **현재 내용 게시**가 외부 게시본을 교체합니다. 공개 범위 변경은 초안 내용을 게시하지 않고 현재 게시본의 접근 권한만 즉시 바꿉니다.

## 로컬 검증과 실제 공개 자료 이전

```sh
# 플랫폼 개발 서버가 실행 중이어야 합니다.
npm run test:platform
```

이 검증은 localhost 주소만 허용합니다. 실제 로컬 Auth 가입, 두 계정의 RLS, Postgres 게시본, Storage 업로드, 서버 이미지 응답과 브라우저 UI를 함께 검사합니다. 운영 DB에는 쓰지 않습니다. 민준호의 기존 공개 자료는 기존 공개용 API로 읽어 로컬의 별도 소유 계정에 가져옵니다. 제목·본문·게시일·슬러그를 보존하고, 사진·첨부 이미지를 로컬 비공개 저장소로 옮깁니다. 로컬 인증의 소유 계정은 운영 계정을 복제한 것이 아닙니다. 운영 이전 시에는 아래 절차로 **기존 운영 계정 UUID**에 연결합니다.

`artifacts/platform/results.json`에 결과를, 같은 폴더의 PNG에 화면을 저장합니다. 로컬 예시 계정의 임의 인증 정보는 무시되는 `artifacts/platform/local-example-owner.json`에만 있습니다. CI는 공개 자료를 확인해 저장한 `tests/fixtures/legacy-public.json`을 사용하므로 운영 서비스와 독립적으로 반복할 수 있습니다. 이 파일에는 기존에 공개된 자료만 있으며 서비스의 신규 계정 기본 데이터로 사용하지 않습니다.

```sh
# CI와 같은 고정 공개 자료로 검사 (PowerShell)
$env:PLATFORM_TEST_FIXTURE='1'
npm run test:platform

# 검사 완료 후 로컬 서비스 중지. 볼륨은 보존합니다.
node platform/scripts/supabase.mjs stop
```

처음 Docker 이미지를 받을 때 시간이 걸릴 수 있습니다. CLI의 에이전트 자동 감지로 DB만 켜지는 경우를 막기 위해 래퍼에서 `--agent no`를 사용하고, 필요한 서비스만 실행합니다. 레지스트리는 GHCR을 기본으로 사용합니다. 내려받기가 멈췄다면 공식 Docker Hub의 동일 버전을 내려받아 `ghcr.io/supabase/<이미지>:<버전>`으로 태그할 수 있습니다. `stop`은 이 프로젝트의 컨테이너만 중지하며 기존의 다른 Docker 프로젝트를 건드리지 않습니다.

## 데이터와 권한

| 데이터 | 역할 | 직접 접근 |
| --- | --- | --- |
| `pf_profiles` | 회원 소유 프로필·테마 초안 | 본인만 읽기·쓰기 |
| `pf_projects` | 프로젝트 원본·순서·대표·탐색 선택 | 본인만 읽기·쓰기 |
| `pf_records` | 이전한 블로그·연구·이력 원문 | 본인만 읽기·쓰기; 1단계 UI는 열람 |
| `pf_assets` | 소유 이미지의 경로·설명 | 본인만 읽기·추가 |
| `pf_publications` | 게시 시점의 스냅샷·공개 범위·공유 토큰 해시 | 본인 읽기; 게시 RPC만 쓰기 |

비공개는 외부 조회가 불가능합니다. 링크 공개는 32바이트 난수의 공유 토큰이 맞아야 하며 탐색에 나오지 않습니다. 공개에서도 게시본에 포함되고 프로젝트의 `discoverable`이 켜진 작업만 탐색 RPC가 반환합니다. 탐색 상세도 같은 조건을 검사합니다. 일반 사용자와 익명 요청은 게시본 테이블이나 다른 사람의 초안을 직접 조회할 수 없습니다. `pf_snapshot`과 이전용 RPC의 실행 권한도 제한합니다.

이미지는 `portfolio-private` 비공개 버킷에 저장합니다. `/media/:id/`가 현재 게시본·공유 토큰·소유권을 확인한 뒤 서버 전용 키로 파일을 읽습니다. 서명 URL로 리디렉션하지 않으므로 링크 회수 후 유효한 다운로드 URL이 따로 남지 않습니다. 공유 페이지와 이미지 응답은 `private, no-store`, 공유 페이지는 `noindex/nofollow/noarchive`입니다. 세션은 HttpOnly 쿠키를 사용하고 서버에서 `getUser()`로 검증합니다. 상태 변경 요청은 동일 Origin만 받습니다.

서버 키는 `SUPABASE_SERVICE_ROLE_KEY`로만 설정합니다. `PUBLIC_` 접두사를 붙이지 않습니다. 키는 브라우저 번들에 넣지 않으며 `.env`를 Git이나 Docker 이미지에 포함하지 않습니다. 로그인 이메일도 공개 프로필에 저장하지 않습니다.

## 운영 Supabase 적용 순서

운영 배포 전 백업을 확보한 뒤 기존 프로젝트에 아래 세 파일을 순서대로 한 번 적용합니다. 기존 테이블과 정책은 유지하며 `pf_` 테이블과 별도 비공개 버킷을 추가합니다.

1. `supabase/migrations/202611120001_platform.sql`
2. `supabase/migrations/202611120002_legacy_import.sql`
3. `supabase/migrations/202611120003_publication_assets.sql`

두 번째 파일은 기존 `site_admins`가 정확히 한 명이면 그 UUID를 소유자로 가져옵니다. 여러 관리자라면 자동으로 선택하지 않습니다. SQL Editor에서 대상 계정을 확인하고 `select public.pf_import_legacy('실제-소유자-UUID');`를 실행하세요. 소유자 지정과 이전 함수는 일반 회원에게 허용되지 않습니다. 다른 사용자의 테마에는 민준호의 자료를 넣지 않습니다.

이전 직후에는 이미지 전송이 끝날 때까지 예시 페이지를 비공개로 유지합니다. 운영 키를 **로컬 파일 또는 배포 환경의 비밀값 관리 기능**에 직접 설정한 뒤, 사이트를 회원에게 열기 전에 다음 명령으로 기존 공개 사진·첨부 파일을 옮깁니다.

```sh
node platform/scripts/migrate-media.mjs 실제-소유자-UUID
```

이 명령은 `platform/.env`를 읽습니다. 먼저 연결 대상 URL을 확인하세요. 운영에서는 기존 `juno31323.me`와 기존 Supabase의 공개 파일을 내려받아 새 비공개 버킷에 저장합니다. 원문은 바꾸지 않고 원래 이미지 주소와 새 이미지 ID의 대응표를 소유 프로필에 보관합니다. 전송 완료·버전 확인 후에만 초기 게시본을 공개합니다. 실패하면 비공개로 남으며 재실행으로 이어갈 수 있습니다. 이미 완료한 이전은 콘텐츠를 덮어쓰지 않습니다. 실패한 전송의 미참조 파일은 추후 소유자 기준으로 정리할 수 있습니다.

기존 사용자도 새 앱에서 같은 Supabase 계정으로 다시 로그인하면 일반 회원과 같은 편집기에 접근합니다. 정적 사이트의 localStorage 로그인 세션을 서버 쿠키로 복사하지 않습니다.

## 배포

GitHub Pages에 이 앱을 올리지 않습니다. Node 24를 실행할 서버가 필요합니다.

```sh
npm run platform:build
npm run platform:start
```

실행 환경에 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `PLATFORM_URL=https://새플랫폼도메인`, `HOST`, `PORT`를 설정합니다. **`PLATFORM_URL`은 빌드할 때도 설정해야 합니다.** Astro가 이 도메인을 허용 호스트에 넣어 서버의 요청 주소·쿠키·Origin 검사·공유 주소를 올바르게 처리합니다. 도메인이 바뀌면 다시 빌드합니다. `platform:start`는 로컬 `.env`가 있으면 읽고, 환경에 이미 있는 변수는 덮어쓰지 않습니다. 배포는 Docker 또는 일반 Node 서버를 사용할 수 있습니다.

```sh
docker build --build-arg PLATFORM_URL=https://새플랫폼도메인 -f platform/Dockerfile -t portfolio-platform .
docker run --rm --env-file /안전한/경로/platform.env -p 8080:8080 portfolio-platform
```

TLS 프록시가 실제 호스트·HTTPS 프로토콜을 서버에 전달하도록 설정하고, Supabase Auth의 Site URL과 허용 리디렉션에 새 도메인 및 `https://새도메인/auth/callback/`을 추가합니다. 운영 회원가입은 이메일 확인과 이메일 발송 설정을 확인한 뒤 엽니다. 로컬에서는 테스트용으로 이메일 확인을 생략합니다.

Docker 최종 이미지에는 서버·클라이언트 빌드와 필요한 의존성만 포함합니다. 정적 파일은 폰트·아이콘·일반 OG 이미지만 복사합니다. 개인 사진과 첨부 파일은 플랫폼의 공개 디렉터리에 넣지 않습니다. 공개 페이지는 이름·소개·공유 메타데이터를 서버 HTML에 포함하고, 링크 공개의 OG는 일반 안내를 사용합니다.

## 도메인 전환

기존 주소 대응은 `route-map.json`의 28개 항목에 정리했습니다. 새 서버 자체도 기존 프로젝트·연구·블로그·쿼리형 글 주소를 308로 연결합니다. 실제 새 배포에서 로그아웃·모바일·이미지·폰트·CSS·JS를 확인하기 전에는 기존 도메인을 바꾸지 않습니다.

GitHub Pages를 기존 도메인의 안내 사이트로 남길 경우:

```sh
# PowerShell 예시. 실제 배포 검증 후에만 지정합니다.
$env:PLATFORM_MIGRATION_TARGET='https://검증한-새플랫폼-도메인'
node platform/scripts/legacy-redirects.mjs
```

생성한 `dist-redirects/` **만** 기존 Pages에 배포하고 기존 CNAME 설정을 유지합니다. 이 폴더에는 이전 HTML만 있으며 개인 이미지 파일은 없습니다. 기존 `dist/`를 함께 올리지 않습니다. 쿼리형 `/entry/` 주소는 Pages에서 JS로 분기하고, JS가 꺼지면 글 목록 링크를 제공합니다. 서버 리디렉션을 사용하는 경우 쿼리형 주소도 JS 없이 308로 연결됩니다.

전환 후에는 이전 원본 이미지 URL도 확인합니다. 기존 `site-images` 버킷은 원래 공개 버킷이므로, **새 앱으로 파일을 옮기는 것만으로 원본 URL이 회수되지는 않습니다.** 새 이미지와 원문을 모두 확인한 뒤 원본 버킷의 공개 설정을 끄거나 이전 완료한 원본만 정리하고, 이전 Pages의 개인 이미지도 더 이상 제공하지 않는지 확인합니다. 이미 외부에 저장·전달된 사본을 삭제할 수는 없습니다. 이번 로컬 작업에서는 운영 원본을 변경하지 않았습니다.

기존 Pages 워크플로는 이번 변경으로 자동 전환하지 않습니다. 새 서버가 아직 없으므로 현재 도메인과 운영 DB의 콘텐츠·권한도 바꾸지 않습니다.

## 범위

회원가입·로그인·온보딩, 프로필·프로젝트, 테마 하나의 4색/밝기/섹션 표시·순서, 대표 작업과 프로젝트 순서, 데스크톱·모바일 미리보기, 게시본·공개 범위·공유 회수, 한국어·영문 기술 검색과 역할 필터, 이전한 글 열람을 구현합니다.

회원용 블로그 쓰기, 직무별 여러 제출 페이지, 만료일, 기업 계정·채용 제안·추천 점수는 후속 범위입니다. 운영 도메인·외부 서버 배포·운영 DB 적용은 이번 로컬 검증 범위에 포함하지 않습니다.
